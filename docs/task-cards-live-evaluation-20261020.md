## 六条失败消息

| 位置 | 输入/现象 | 代码和模型输出解释 | 后续修改方向 |
| --- | --- | --- | --- |
| lifecycle 第3步 | “之前等数据的阻碍解除了”，仍存在有效 blocker | 关联正确撤销旧阻碍，但抽取把“阻碍已解除”又分成 blocker 并作为新有效细节追加 | 解除信息应为 progress/outcome，旧 blocker 进入历史 |
| subjects 第3步 | “同事小明…整理完了”，小明任务仍为 todo | 前次 subject 为“小明”，此次为“同事小明”，主体字符串筛选未召回原卡 | 有证据的同人称谓归一；不能只放宽所有人物匹配 |
| reference 第2步 | “这个已经完成了”，仍 todo 并进入待确认 | 模型把前文的“今晚”放入当前细节 evidence_span；当前原文无该片段，被校验拒绝 | 指代继承任务身份，当前更新只输出当前证据支持的变化 |
| temporal 第1步 | 本周/下周日期范围错误 | 2026-10-20 是周二，模型用当天起七天代替自然周；正确范围为 10-19～10-25、10-26～11-01 | 日期边界由明确规则计算或验证 |
| temporal 第2步 | 本周截止改周日未生效 | 输出旧字段 entities，被新结构禁止额外字段的校验拒绝；轮次日期表达也变化 | 消除新旧任务提示规则冲突；轮次采用稳定身份 |
| condition 第1步 | 条件和备份要求保存了，却额外产生待确认 | 抽取另建备份候选，关联又试图将 time 覆盖部署卡的 requirement，类型校验拒绝 | 明确任务与前置要求的拆分规则，避免自相矛盾的关联计划 |

条件场景中“备份”是否独立成任务可另行约定；本次实际失败点是生成了无法落地的重复候选和多余待确认，不是断言备份永远不能独立成任务。

初步试跑还见到同一轮次不同写法被字符串过滤，导致明确重开/延期找不到原任务。它不计入本次正式运行的独立失败数；正式运行的取消及重开场景通过。
