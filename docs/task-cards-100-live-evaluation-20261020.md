## 已确认的主要问题

| 专业描述 | 简单解释及真实例子 |
| --- | --- |
| 主体、实例使用不稳定文本关联 | “李若宁”和“若宁”生成两张卡；“一次”改说“刚才那次”也重复建卡；“本次”改说“原来这次”重开失败。 |
| 多任务状态覆盖不足 | “审核完成、发送未完成”只更新发送卡，审核卡仍是 todo。 |
| 阻碍分类及替换计划错误 | “阻碍已解除”又保存为有效 blocker；“尚未安装”也被当成阻碍；解除部分阻碍时跨类型替换被拒绝。 |
| 结构字段与抽取范围不稳定 | 输出 entities、description_note 等非法字段而进入待确认；把“分别记录”当成第三个待办；否定计划和引用文字也产生无谓待确认。 |
| 日期未统一为稳定轮次 | 有时仅保存“上周/本周”或“某日所在周”，没有约定的起止范围；延期时同一周的文本表示变化，关联失败。 |
| 纠正及转交缺少正确更新路径 | 明确纠正误报完成仍被当作未经授权重开；改会议室对象被拒绝；换负责人后旧任务被取消、新负责人任务未接上。 |
| 同义细节去重不足（自动断言漏检） | 重复提醒缺同一份营业执照，保存两条有效阻碍；“低温要求不变”又生成一条低温要求。 |

## 评分审计

原始评分为 195/222、75/100。`references_04` 第2步及 `references_07` 第1步实际上已在数据库生成待确认，但服务的 results 数组为空。旧评分器只看 results，错误地判定没有待确认。

评分器 v3 增加按原消息 note_id 核对数据库待确认，并为今后的运行保存当步 pending_items；只对保存的同一批输出重新评分，结果变为 197/222、77/100。5 个评分器回归测试通过。原始 summary.json 与 steps.jsonl 未覆盖。

另两条保留在自动失败中、人工判为规则误报：

- `details_01` 第1步：条件“周日不下雨”完整保存在 time.condition；断言强制 requirement，类型限制过严。
- `details_03` 第2步：有效纸张要求已改为 A5，A4 仅出现在“原要求作废”备注中；字面禁词误报。

自动通过项抽查发现 `details_05` 第2步、`details_08` 第2步有同义要求重复；`history_duplicates_06` 第2步有同义阻碍重复，违反其 oracle。这里只做了失败复核和部分通过项抽查，不给未经完整人工复核的“语义准确率”。
