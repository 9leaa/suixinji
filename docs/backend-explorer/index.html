Length 为保留消息数，Pending 为已投递但未确认数，Lag 为尚未投递数；它们不是同一指标。

队列命令与处理顺序
XADD→XREADGROUP→PostgreSQL claim→handler→DB complete / retry / dead→XACK
XREADGROUP 分派给同组消费者，未 ACK 的消息进入 PEL；XAUTOCLAIM 接管超时未确认消息。XACK 清除 Pending，不删除 Stream 消息。
派发一张工单，做完后签收。签收是“任务已交代”，不是把队列历史直接删掉；超时未签收可以交给其他 Worker。
处理失败或延期时，先把 retry / dead_letter 状态写入 PostgreSQL，再确认旧消息；到期重试由新 Outbox 再投递。不能把 XACK 理解为“业务一定成功”。Stream 使用近似 MAXLEN 裁剪，保留长度不是永久消息档案。

分布式可靠性 · 重复、并发与故障
通知可以重复，事实需要可校验；系统通过状态机、幂等和所有权校验降低重复处理。
任务状态机
blocked→queued→running→completed
running→retry→queued + 新 Outbox失败次数耗尽 → dead_letter
等待水位时为 blocked；认领成功进入 running；处理异常增加 failure_count。RetryLater 延期增加 defer_count，不消耗普通失败次数。cancelled / superseded 等终态也会被消费者识别。

每一道保护解决什么问题
典型故障如何恢复
故障时刻系统已有证据恢复路径 / 边界
数据库提交前失败事务未提交上游重试；不能报告消息已持久化。
数据库提交后，Redis XADD 失败Inbox + Task + 待发布 OutboxRelay 记录失败、退避重试；超过发布次数进入 Outbox dead。
XADD 成功，标记 published 前退出Stream 已有通知，Outbox 未确认租约过期后可能再次投递；Task 唯一键、认领和状态校验抵御重复。
Worker 处理中退出Redis Pending + DB running / leaseXAUTOCLAIM 接管通知；数据库租约过期后才允许重新认领。
完成数据库提交，XACK 前退出DB completed，旧消息仍 Pending再次读取时识别终态并 ACK，不重新执行处理器。
飞书发送超时Delivery 记为 unknown不盲目重发；unknown 可能已经送达，也可能没送达，需要核查。
这是至少一次通知 + 幂等与所有权控制，不是端到端严格 exactly-once。Redis 数据丢失后，仅靠已标记 published 的 Outbox 不会自动重建所有未完成通知；恢复时需对照 PostgreSQL 任务与队列，按切换手册核查。
