# 随心记偏好记忆系统技术方案

- 版本：v1.0
- 日期：2026-10-18
- 状态：待实施
- 范围：偏好记忆卡片、写入关联、查询证据、定期整理、通用 pending 反馈及问题数据集。

最终方案采用“偏好卡片＋具体偏好＋原文来源”的结构。以“谁＋偏好对象”定位卡片，写入时允许追加，后台定期整理；查询时把相关偏好、原文和消息时间交给模型；处理不了的内容统一进入 pending 并及时反馈。

本文件是首版实施规格。方案已结合当前随心记代码检查；文中的数量阈值是建议初值，后续通过实际数据调整。保存本文件不代表已实施代码修改、数据迁移或定时任务。

## 一、范围与核心约定

| 设计项 | 最终约定 |
|---|---|
| 偏好定位 | 同一用户空间内，“主体＋偏好对象”定位一张卡片 |
| 主体 | 默认“用户”；明确人物保留关系或职位，如“同事小明” |
| 指代 | 结合近期消息解析；无法确定则 pending |
| 对象名称 | 普通名称优先中文，保留原始表达 |
| 对象提取 | “拿铁咖啡”提取“咖啡”，拿铁进入具体描述；单说“拿铁”则提取“拿铁” |
| 属性表达 | 使用自然语言条件和描述，不预设糖度、温度等大量字段 |
| 写入方式 | 可以新增、追加、更新、补充来源，不强制覆盖已有细节 |
| 整理方式 | 时间与数量双触发，只处理发生变化的内容及必要关联 |
| 查询方式 | 提供对应与相似偏好、原文、消息时间、有效状态，由模型综合回答 |
| 处理失败 | 所有消息类型统一 pending，及时反馈“原文＋原因” |
| 质量改进 | 收集问题现场，经审核形成数据集，接入回归评测 |

需要一直保持三个区别：

| 专业概念 | 直白解释 |
|---|---|
| 已保存、待整理 | 内容已经理解并记住，只是还没有合并或归纳 |
| pending | 内容尚未可靠处理，需要补充信息或系统恢复 |
| 疑似问题 | 怀疑系统处理有误，需要检查；不等于已经确认错误 |

## 二、偏好卡片的数据结构

业务字段固定为四个：

| 字段 | 含义 |
|---|---|
| `subject` | 谁的偏好 |
| `preference_object` | 偏好对象 |
| `attitude` | 用户明确表达的总体态度 |
| `details` | 带条件和来源的具体偏好 |

示例：

```json
{
  "subject": "用户",
  "preference_object": "咖啡",
  "attitude": "喜欢",
  "details": [
    {
      "id": "d1",
      "attitude": "喜欢",
      "condition": "",
      "description": "喜欢喝咖啡",
      "source_ids": ["s1"]
    },
    {
      "id": "d2",
      "attitude": "不喜欢",
      "condition": "早上",
      "description": "早上不喜欢喝咖啡",
      "source_ids": ["s2"]
    },
    {
      "id": "d3",
      "attitude": "喜欢",
      "condition": "工作时",
      "description": "工作时喜欢低糖拿铁咖啡",
      "source_ids": ["s3"]
    }
  ]
}
```

具体字段规则：

- `condition` 使用自然语言，例如“早上”“工作时”“和朋友一起时”；空字符串表示没有说明条件，不是适用于所有场景。
- `description` 必须保留完整含义，包括低糖、拿铁、程度、原因等，不能只剩“喜欢咖啡”。
- `source_ids` 指向来源记录，由程序绑定，不让模型编造。
- 每个细节有独立 `id`，用于明确更新目标。
- 细节的态度支持“喜欢、不喜欢、无所谓、不确定”。
- 卡片总体态度额外支持“未说明”；如果多条总体表达尚无法消解，则标记“待确认”。

总体态度不能根据局部偏好擅自推导。只有“工作时喜欢低糖拿铁咖啡”，不能推断总体喜欢咖啡。卡片顶部的态度必须有对应细节和来源支持，它只是方便展示的结果。

系统元数据与业务字段分开：

| 元数据 | 用途 |
|---|---|
| 卡片 ID、空间及所属用户 | 唯一标识和数据隔离 |
| 卡片版本 | 防止并发更新覆盖 |
| 细节状态 | 当前有效、历史、撤回 |
| 来源记录 | 关联笔记版本、原文片段、消息时间 |
| 处理与整理记录 | 幂等、重试、排查问题 |
| 结构版本 | 新旧数据兼容 |

原始笔记、来源与历史版本不因整理而删除。

## 三、抽取规则：主体、对象和指代

### 3.1 主体规则

| 消息 | 抽取主体 |
|---|---|
| 我喜欢咖啡 | 用户 |
| 喜欢喝咖啡 | 用户 |
| 我的同事小明喜欢咖啡 | 同事小明 |
| 我的领导老王喜欢茶 | 领导老王 |
| 小明喜欢咖啡 | 小明 |
| 上文明确提到同事小明，随后说“他喜欢咖啡” | 同事小明 |
| 上文同时出现小明和老王，无法判断“他” | pending |

默认“用户”只适用于没有明确第三人称指向的表达。“他”解析失败时，不能退回“用户”。

首版复用当前近期消息上下文机制，保留指代来源消息及证据。超出可用上下文或有多个候选时，及时反馈，而不是猜测。

关系称谓也不能随意合并：“领导老王”和“同事老王”可能是同一个人，也可能不是。没有证据时分别保留，允许建立待确认关联。

### 3.2 对象规则

| 消息 | 偏好对象 | 具体描述 |
|---|---|---|
| 喜欢 coffee | 咖啡 | 喜欢咖啡 |
| 喜欢低糖咖啡 | 咖啡 | 喜欢低糖咖啡 |
| 喜欢拿铁咖啡 | 咖啡 | 喜欢拿铁咖啡 |
| 喜欢拿铁 | 拿铁 | 喜欢拿铁 |
| 喜欢咖啡味香水 | 香水 | 喜欢咖啡味香水 |

名称有明确中文译名时使用中文。品牌、专有名词或多义词没有可靠对应时保留原名，避免错误翻译。

还需识别消息是否真的在表达偏好：

- “今天喝了咖啡”是行为，不能自动推断喜欢。
- “今天不喝咖啡”可能是计划，不等于不喜欢。
- “小明说我喜欢咖啡”需要区分偏好主体与信息提供者。
- 提问、假设、引用文案不能直接写成用户事实。
- “可能喜欢”“不讨厌”“没那么喜欢”不能简单转换为强烈正向或负向。

这些规则放进偏好抽取 Prompt 和回归样例中。程序负责检查结构、枚举和证据引用，模型负责语义理解。

## 四、写入前关联：先找卡片，再理解新旧内容的关系

每条偏好消息按以下流程处理：

```text
保存原始消息
→ 抽取偏好候选
→ 解析主体与对象
→ 检索对应及相似偏好
→ 携带原文和消息时间进行判断
→ 新建 / 追加 / 更新 / 补充来源 / 关联 / pending
→ 保存决策、来源和版本
```

一条消息可以产生多个候选，例如“喜欢咖啡但不喜欢茶”。能处理的部分正常处理，不能处理的部分单独 pending。

检索采用四路召回：

| 通道 | 作用 |
|---|---|
| 精确定位 | 找同主体、同对象卡片 |
| 名称与对象关联 | 找中英文同义名称、相关品类 |
| 关键词检索 | 找低糖、拿铁、工作时等具体表达 |
| 语义检索 | 找表达不同但含义接近的内容 |

召回结果必须：

- 先限定空间和主体。
- 不按极性过滤，正向与负向都能找出来。
- 保留精确卡片，不能因为向量分数低被挤掉。
- 相关不等于相同，不能仅因相似就覆盖。
- 对已有冲突，尽量把双方一起提供。

没有历史偏好时正常新增。第一次说“不喜欢咖啡”，直接创建负向偏好，不需要先存在“喜欢咖啡”。

对象关联区分三类：

| 关系 | 示例 | 是否可直接统一定位 |
|---|---|---|
| 同义 | coffee、咖啡 | 可以，确认语义相同后 |
| 品类关系 | 拿铁、咖啡 | 不可以，只扩展检索 |
| 普通相关 | 咖啡、茶 | 不可以，作为关联背景 |

这样既保留“单说拿铁就存拿铁”的规则，也能检索到咖啡卡片中有关拿铁的细节。

## 五、即时写入：允许追加，明确时才更新

模型输出有限操作，程序执行，避免模型无约束重写整张卡片。

| 操作 | 使用条件 |
|---|---|
| 新建卡片 | 没有对应主体和对象 |
| 追加细节 | 新场景、新限定、新说明，或关系尚未整理清楚 |
| 更新细节 | 新消息明确修改某项已知偏好 |
| 补充来源 | 内容重复，没有实质变化 |
| 关联卡片 | 发现相关对象或跨卡片相似事实 |
| pending | 无法可靠理解、定位或执行 |

例如：

| 旧内容与新消息 | 处理 |
|---|---|
| 无记录 →“我不喜欢咖啡” | 新建 |
| 喜欢咖啡 → 再次说喜欢咖啡 | 补充来源 |
| 早上不喜欢 →“晚上喜欢咖啡” | 追加 |
| 早上不喜欢 →“现在早上也喜欢了” | 明确更新早上那项，保存旧版本 |
| 早上不喜欢 →“工作时喜欢咖啡” | 允许追加，交给查询或整理处理交叉场景 |
| 喜欢低糖 →“喜欢高糖” | 默认追加，不能推断低糖已经不喜欢 |
| “刚才说错了，是小明喜欢” | 更正归属，不当作用户态度变化 |

新内容明确、只是与旧内容的关系没有整理清楚时，可以记为“已保存、待整理”，不必每次都打断用户。

但是，如果用户说“把之前那条改掉”，而有多个可能目标，则应 pending，不能任选一个。

重复表达只增加独立来源，不制造大量相同细节或无意义版本。多个来源也不能被简单当成“多数票”，压过一次明确的新纠正。

## 六、统一 pending 与即时反馈

这是所有消息处理类型共用的机制，包括偏好、任务、语义、事件、分类不明确，以及查询无法完成等情况。

pending 原因分为两类：

| 类型 | 示例 | 后续 |
|---|---|---|
| 需要用户补充 | 指代不明、修改目标不明 | 等待用户回复 |
| 系统待恢复处理 | 模型调用失败、存储失败、容量限制 | 自动重试或系统处理，必要时人工介入 |

通知格式统一：

> **这条消息有部分内容待处理**
> 原文：他喜欢喝咖啡。
> 原因：前文同时出现同事小明和领导老王，无法确定“他”指谁。
> 需要补充：这里指的是哪一位？

系统故障的通知则说明：

> 原因：记忆处理服务暂时不可用，消息已保存，将自动重试。

如果原文实际上尚未保存成功，就必须明确说未保存，不能错误承诺。

通知与恢复规则：

1. 发现 pending 后立即创建通知任务，不等每日汇总。
2. 保留原消息 ID、原文、失败阶段、原因、已完成部分。
3. 同一个问题重试不重复发送相同通知。
4. 用户回复绑定到对应 pending 项；存在多个待处理项时，通过回复关系或编号区分。
5. 解决后更新状态，并发送简短结果通知。
6. 通知发送失败保留重试任务，不能把“未通知成功”当作“已通知”。
7. 正常去重、明确无需记忆的闲聊，不属于处理失败。

仅仅有相反偏好也不一定 pending。例如早上不喜欢、晚上喜欢，是正常差异。

## 七、卡片数量限制与定期整理

首版建议采用以下可配置参数：

| 参数 | 建议初值 |
|---|---:|
| 卡片有效细节达到多少条触发整理 | 10 条 |
| 卡片有效细节硬上限 | 20 条 |
| 单用户自上次整理后的新变化阈值 | 30 条 |
| 日常整理间隔 | 24 小时，且有变化 |
| 跨卡片关联检查间隔 | 7 天，且有相关变化 |

触发方式为任一条件满足即可入队。

统计“新变化”时：

- 按独立候选或来源版本去重。
- 消息重试不重复计数。
- 新增事实、明确修改、有效补充计入变化。
- 整理生成的摘要不算用户新输入。
- 成功处理到哪个进度，只清除对应范围的变化标记。

卡片达到 10 条后，后续只有发生新变化才再次触发整理，避免同一张卡片一直空转。

达到 20 条时：

1. 暂停向卡片继续追加有效细节。
2. 原文和新候选进入待处理队列。
3. 优先触发该卡片整理。
4. 向用户反馈原文及“卡片容量已满，等待整理”的原因。
5. 整理释放容量后继续处理，并更新 pending 状态。

如果 20 条都是不能合并的真实差异，不能为了腾位置删除事实。首版应保留容量 pending，停止无效重复整理，允许人工处理或调整配置上限。这个限制必须明确，不能承诺整理一定能压缩到固定条数。

## 八、整理进程的职责与边界

整理读取卡片、关联卡片、来源原文和消息时间，提出有限操作：

| 整理动作 | 行为 |
|---|---|
| 去重 | 合并重复表达，合并来源 |
| 同义整理 | 统一“工作时／工作的时候”等确定等价表达 |
| 变化整理 | 新旧状态明确时，将旧状态保留为历史 |
| 场景整理 | 保留不同条件下的真实差异 |
| 对象关联 | 建立咖啡与拿铁等检索关系 |
| 跨卡片检查 | 识别相同具体事实，建立关联或去重展示 |
| 来源检查 | 发现原文缺失、描述不受原文支持 |
| 摘要更新 | 生成简短概括，仍能回到具体细节与来源 |

不得执行：

- 为减少数量而抹掉条件。
- 因为表达相似而合并不同人物。
- 把旧摘要当作新增事实反复提炼。
- 仅因整理时间较新，就覆盖原消息中的偏好。
- 将仍然有效的差异伪装成“已过时历史”。
- 将“系统尚未判断清楚”写成确定结论。

每次整理保存输入版本、操作、来源、前后差异及运行结果。读取和模型调用完成后，提交前再次检查版本；期间发生新写入则重新判断，不能覆盖新内容。

整理失败不推进成功进度。任务重复执行也不能重复追加相同内容。

## 九、查询：相关记忆、原文与消息时间一起提供

查询流程：

```text
理解问题中的主体和对象
→ 检索对应卡片
→ 扩展关联与相似偏好
→ 获取相关细节及历史变化
→ 回读来源原文
→ 组装证据包
→ 模型综合回答并引用来源
```

默认向最终模型暴露：

```json
{
  "subject": "用户",
  "preference_object": "咖啡",
  "description": "早上不喜欢喝咖啡",
  "relevance": "直接相关",
  "status": "当前有效",
  "original_text": "但我不喜欢在早上喝咖啡",
  "message_time": "2026-10-18T08:00:00+08:00",
  "note_id": "note_123"
}
```

写入时间和整理时间保留在系统内部，不默认提供给最终模型。

时间处理规则：

- 消息时间来自原始消息，不能使用记忆更新时间替代。
- 原文说“去年”“最近”“仅本周”等，保留原文让模型结合消息时间理解。
- 首版不强制增加独立生效时间字段，也不宣称支持完整的自动过期逻辑。
- 来源时间缺失时明确为空或未知，不伪造。
- 同一条整理后的细节有多个来源时，保留各自消息时间。

证据选择规则：

- 同时包含正向和负向偏好。
- 保留关键例外和冲突双方。
- 相似对象明确标记为相关，不能伪装成同一对象。
- 原文通过真实笔记引用获取，不让模型根据摘要重构。
- 长笔记先提供相关片段，必要时继续读取全文。
- 超过上下文预算时分批读取，不能只取前几条就声称信息完整。
- 待处理内容可以以“待处理原始消息”提供，但不能包装成已确认记忆；尤其不能把主体未解析的内容归给用户。

最终模型负责解释关系：

> 你总体喜欢咖啡，但早上不喜欢；工作时偏向低糖咖啡。早上工作时的具体偏好还不明确。

模型不能把自己的推断直接写回记忆。它可以提交疑似问题，交给后续处理。

## 十、问题记忆收集与数据集

新增“记忆问题记录”，覆盖抽取、关联、写入、查询和整理全过程。

| 问题类型 | 示例 |
|---|---|
| 主体错误 | 同事的偏好记成用户 |
| 指代错误 | “他”错误指向另一人 |
| 对象错误 | 咖啡味香水记成咖啡 |
| 条件遗漏 | 早上不喜欢被写成总体不喜欢 |
| 召回遗漏 | 没找到旧偏好或关键例外 |
| 更新错误 | 修改了错误场景 |
| 时间错误 | 去年表达被当成当前偏好 |
| 来源错误 | 引用原文不支持结论 |
| 整理错误 | 合并后丢失真实差异 |
| 回答错误 | 模型无依据消解冲突 |

问题来源包括用户反馈、程序校验、整理检查、回答后的证据检查，以及少量正常记录抽样检查。

pending 和问题记录可以关联，但不能混为一谈。用户表达本来就有歧义，不一定代表系统能力缺陷；反过来，系统错误也可能没有触发 pending。

每条问题保存：

- 当时的消息或问题，以及必要前文。
- 操作前的相关记忆快照。
- 实际召回内容、原文和消息时间。
- 模型抽取结果及拟执行操作。
- 最终写入结果或回答。
- trace ID、模型、Prompt、代码及结构版本。
- 用户反馈、审核结论、期望结果。

问题流转：

```text
疑似问题
→ 待审核
→ 已确认 / 正常差异 / 信息不足
→ 已标注样例
→ 回归评测
→ 修复验证
```

模型提出的“标准答案”只能作为建议，未经审核不能直接成为评测真值。

数据集分四组：

| 数据集 | 评测重点 |
|---|---|
| 抽取集 | 主体、对象、态度、细节、指代 |
| 写入关联集 | 应召回什么、应该新增还是更新、改哪一项 |
| 查询回答集 | 对应及相似证据、原文引用、冲突表达 |
| 整理集 | 去重效果、信息保留、来源和历史完整性 |

导出为 JSONL，支持直接回放。相同对话及其改写按组划分开发集和测试集，避免同一案例泄漏到两边。导出用于项目共享的样例做一致去标识处理，保留主体关系和时间关系。

反馈给项目负责人的形式：

- pending：发现即反馈。
- 已确认严重错误：及时提示。
- 一般问题：问题列表与有新增内容时的每日摘要。
- 已审核样例：可下载数据集和回归报告。

报告应区分疑似与已确认数量，不把正常偏好差异统计成系统错误。

## 十一、程序模块与存储落地

当前系统已有候选检索、裁决、来源、版本、调度、反馈和 trace，可以逐步改造。

| 模块 | 改造内容 |
|---|---|
| 抽取 Schema、Prompt | 新字段，主体默认规则，对象中文规则，指代示例 |
| 候选检索 | 精确卡片、对象关联、关键词和语义多路召回 |
| 裁决模块 | 支持卡片内追加、更新、补来源，不强制覆盖 |
| 写入模块 | 明确操作目标、版本检查、来源绑定、事务提交 |
| 查询证据模块 | 回读原文，提供消息时间及相关状态 |
| 整理调度 | 新增数量触发和偏好专项整理 |
| pending 模块 | 通用原因、即时通知、用户回复关联、重试恢复 |
| 质量模块 | 问题快照、审核、样例导出与评测 |

首版存储建议：

- 使用现有记忆记录承载偏好卡片。
- 主体、对象和总体态度映射到现有相应字段。
- 具体偏好及来源引用放入版本化 JSON 结构。
- 复用原始笔记、来源与历史版本机制。
- 增加对象关联、pending 状态及通知、整理运行状态、质量问题记录。
- 对“空间＋所属用户＋规范化主体＋规范化对象”建立卡片唯一定位约束。
- 所有细节修改都重新生成检索文本，并刷新相应索引；索引尚未更新时，精确定位仍可读取数据库最新内容。

一次写入事务必须同时处理卡片变化、来源、版本和决策记录。提交前验证目标卡片与细节存在、所属主体正确、版本未过期；同一候选重复执行不得重复写入。

旧数据迁移按新结构版本执行：

1. 先将同主体、同对象的旧偏好投影为卡片，不删除原记录。

5. 查询阶段避免同时把迁移前后副本当成两份独立证据。

## 十二、实施顺序与验收标准

建议顺序：

1. 先建立可回放测试样例：覆盖已讨论的偏好、指代和更新场景。
2. 建立通用 pending 与问题现场记录：确保后续处理失败可通知、可复现。
3. 实现卡片结构、抽取、关联召回和即时写入。
4. 实现查询证据包和原文时间回读。
5. 实现数量限制及定期整理。
6. 补齐问题审核、数据集导出与回归评测。
7. 验证旧数据迁移，再逐步启用。

首轮验收必须覆盖：

| 场景 | 必须达到的结果 |
|---|---|
| 首次说不喜欢咖啡 | 正常新建，无需先有喜欢 |
| 总体喜欢、早上不喜欢、晚上喜欢 | 同一卡片保留三种表达 |
| 早上改为喜欢 | 只改对应细节，保留历史 |
| 工作时喜欢与早上不喜欢 | 可追加，不强行覆盖 |
| 重复表达多次 | 不重复堆积有效细节 |
| 同事小明与用户都谈咖啡 | 不串主体 |
| “他”有明确前文 | 正确解析并关联证据 |
| “他”有多个候选 | pending，反馈原文与原因 |
| coffee、拿铁咖啡、拿铁 | 按约定提取，并能关联检索 |
| 去年消息今天整理 | 不因整理时间新而覆盖近期表达 |
| 卡片达到数量限制 | 不丢原文，有明确 pending 与恢复路径 |
| 整理无法压缩真实差异 | 不删事实、不无限重试 |
| 整理期间出现新写入 | 新内容不被旧快照覆盖 |
| 查询存在关键例外 | 证据包包含例外及原文 |
| 发现处理错误 | 能保存现场并形成审核后的回归样例 |

验证分为规则与模拟模型测试、真实模型测试、本地存储测试、PostgreSQL 并发测试和消息反馈完整流程测试，分别报告结果。模拟模型测试通过，不能替代真实模型的理解能力验证。

首版的主要边界是：允许自然语言细节与模型判断，不实现完整条件逻辑引擎；不要求每次写入即时合并；遇到确实无法处理的情况，保留原文、明确 pending、及时反馈，而不是猜测或静默丢失。
