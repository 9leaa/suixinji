# 任务关联召回与全局主体规则变更

分支：`codex/task-memory-cards`。仅修改本地代码、测试和评估产物；未部署、未修改生产卡片或原消息。

## 处理规则

- 全局主体规则用于任务、偏好、事实和事件抽取。公共入口提供可信账号名称和用户 ID；“我”、本人、无明确主体且无第三人指代的陈述归用户。用户自称与账号身份绑定；明确第三人及其上下文不得改归用户。结构化主体仍展示“用户”，`scope.subject_id` 保存账号身份。
- 所有记忆抽取都提供最近最多三条前文，处理无显式代词但省略了主体的消息。原来的“仅遇到指代词才提供前文”测试已改为验证这个新行为。
- 任务卡片先按空间、所属用户、有效性隔离，然后独立执行来源引用、同主体、任务名称词片匹配、向量相似度四路召回。取并集，按卡片 ID 去重，用 RRF 融合名次，优先保留明确来源；每路普通候选最多 30 张，最终普通候选最多 30 张，明确来源不被截断。
- 向量通过现有 `embed_text` 客户端真实生成，对主体、任务和轮次组成的身份摘要检索。缓存包含模型/端点/维度/摘要指纹；进展和历史不进入身份向量。首次遇到未缓存的历史卡片会补向量，存在冷启动成本；本版使用本地余弦排序，尚未做大规模索引压测。
- `todo`、`done` 都能召回，已删除、撤回、过期及其他用户的卡片不能参与。召回审计保存在 `memory_workflow_state.kind=task_retrieval`，包括各路分数、最终候选与向量通道状态。向量失败会明确记录 unavailable，并保留其余召回结果。
- 写入时不再因人物/轮次文字不同直接拒绝。模型必须对变更的文字明确判定同一身份/同一次任务并说明证据。明确不一致、互不相交的日期/数字轮次、无依据重开仍被拒绝。已存在的轮次展示不会被“刚才那次”覆盖。明确来源也会阻止快捷精确匹配误选另一张卡。
- 通用仓库函数 `hybrid_adjudication_candidates` 未改动，任务卡片已切换到专用四路召回；其他调用方不受这次召回策略变更影响。

## 验证

1. 165 项测试通过，覆盖公共主体归一、同名第三人、账号隔离、任务卡片、偏好、抽取、回答身份规则、任务状态及评分器。身份改写的服务级测试使用固定模型输出，验证召回→校验→原卡更新，不代表真实模型准确率。
2. 真实向量冒烟通过：`text-embedding-v4`，1024 维；“若宁盘点相机器材”与“李若宁清点摄影设备”的相似度约 0.601，高于“预订餐厅”的约 0.284；来源指向候选仍排第一。结果：`eval/reports/task-recall-vector-check-20261021.json`。
3. 真实模型尝试重跑原 9 条问题所在的 8 个场景（20 步），记录于 `eval/results/task-recall-fix-20261021/`。原始计分为 7/20、0/8 完整场景，但存在大量 DeepSeek HTTP 402 `Insufficient Balance`；这不是有效修复验收结果，不能据此宣称那 9 条已全部修复。少量成功响应仍出现原有任务输出契约问题（例如多输出 `entities`），本次未放宽字段契约。
4. 生产数据与旧评估快照保持原样，未批量修复已有重复卡片。
